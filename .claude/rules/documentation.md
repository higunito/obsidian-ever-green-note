# ルール：ドキュメント作成

`docs/` と `tmp/` の設計・仕様・計画文書を書く／更新するときの規則。

## 言語・文体

- **日本語**で書く。
- 実装者ごとに解釈が割れないよう、**曖昧さを排除**し細粒度で書く（「だいたい」「適宜」で逃げない）。

## 文書の役割分担（混ぜない）

- `docs/design.md`（設計書）：情報設計・データモデル・システム構成・コンポーネント・世界観・非機能。**How ではなく What/Why と構造**。
- `docs/specification.md`（機能仕様書）：画面ごとの目的・レイアウト・操作・状態・エラー（SC-000〜SC-015）。
- `tmp/v1-first/implementation-plan.md`（実装計画）：Phase 別・依存順・チェックボックスの作業手順。

## DRY と整合

- **一つの事実は一箇所に書き、他からは参照**する（相対リンク）。同じ内容を複数文書に転記しない。
- 仕様変更は **design → specification → implementation-plan の順に波及**させ、`grep` で関係箇所を洗い出して整合を取る。齟齬を残さない。
- 変更したら各文書末尾の **変更履歴に追記**する。

## 用語・表記

- 用語は `docs/design.md` §13 用語集に従う。
- **ゲーム内名称は `docs/design.md` §3.3 の対応表を正**とする（例：Garden=`FRAGMENTS`、Essays=`ARTICLE`、Collections=`INFLUENCE`、Projects=`PROJECTS`）。ナビは常にゲーム名＋通常名を併記。
- 相互リンクは相対パス。見出しへのアンカーは GitHub 規則（記号・全角括弧・バッククォートを除去、空白→ハイフン）に注意し、リンク切れを出さない。

## 参考資料の扱い

- `reference/` は出典・参考であり **正典ではない**。設計判断は三文書に落とす。
- コンテンツ契約に関わる記述は `reference/obsidian/README.md` と矛盾しないようにする（矛盾する場合は Vault 側を先に直す方針を明記）。
